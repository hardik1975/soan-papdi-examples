# CORDIC 

This project implements a hardware-based CORDIC algorithm on the SOAN PAPDI FPGA to calculate sine and cosine values of any angle. It communicates with an RP2040 MCU (you can use any) using SPI to take inputs and return results.

## What is CORDIC and why use it?

Calculating trig functions like sine and cosine normally requires complex floating-point hardware or heavy lookup tables that consume a lot of memory.

CORDIC (Coordinate Rotation Digital Computer) solves this by computing trig functions using only basic shift and add operations. Instead of multiplying complex math formulas, it iteratively rotates a vector step-by-step using pre-calculated arc tangent values until it aligns with the target angle. This makes it super fast, tiny, and perfect for FPGAs where we don't want to use DSP blocks or massive LUTs.

## Files

* `top.v` - Top-level module that instantiates the internal oscillator, SPI target, and CORDIC engine.
* `spi_target.v` - Handles 32-bit SPI slave communications with the RP2040.
* `cordic_circular.v` - Core iterative CORDIC, fixed-point Q1.15 vector rotations.
* `cordic.ino` - RP2040 Firmware.

## Understanding `cordic_circular.v`

Brief of what CORDIC is in terms of hardware.

### Rotating a vector by tiny known angles

So instead of computing sine/cosine directly, CORDIC starts with a vector of known length pointing along the x-axis, and rotates it step by step until it's pointing at target angle. Each step rotates by a fixed pre known angle (like 45°, then 26.565°, then 14.036°, and so on — these are the `atan` values in the lookup table). Whether you rotate clockwise or counter-clockwise at each step depends on whether you've overshot or undershot the target angle so far.

Rotating by these specific angles only needs shifts and adds, no multiplies. That's the `x_shift` and `y_shift` wires (`x >>> i`, `y >>> i`) — each iteration just shifts the vector components by `i` bits instead of multiplying by `tan(angle)`.

After 15 iterations (`i` goes from 0 to 14), `x` holds cosine and `y` holds sine, scaled up by a constant.

### Why the quadrant check at the start

CORDIC in its basic form only converges cleanly for angles between -90° and +90°. So before starting the rotation loop, it checks which half of the circle the angle falls in:
- If the angle is beyond +90° (`> HALF_PI`), we start the vector already rotated 90° and only rotate the *remaining* angle.
- If it's beyond -90°, same idea but rotated -90°.
- Otherwise, start pointing along x-axis as normal.

This trick lets the same 15-iteration loop handle the full 0°-360° range without needing separate logic for each quadrant.

###  `K_FACTOR` constant 

Each rotation step doesn't just rotate the vector — it also slightly lengthens it (a side effect of the way this simplified rotation math works). After 15 iterations, the vector has grown by a fixed, predictable amount — about 1.647x. So instead of correcting for this after the fact, we just start the vector at length `K_FACTOR = 19898` (in Q1.15 fixed point, that's roughly 0.6072 — the inverse of that growth factor). By the time all 15 rotations are done, the length works itself back out to 1.0.

### Why `x`, `y`, `z` are 18 bits when I/O is 16 bits

The extra 2 bits are guard bits — headroom so intermediate math doesn't overflow before the final saturate step clips it back down to a clean 16-bit signed value. Without them you'd get wraparound errors on quadrant angles (this is why the `sat()` function exists).

## How it works

The RP2040 sends an angle in degrees over SPI. The FPGA reads the 16-bit angle value, converts it into signed fixed-point format, and starts the CORDIC rotation loop.

Because CORDIC is pipelined over SPI, sending a 32-bit SPI transaction pushes the new angle in while pulling out the calculated Cosine (first 16 bits) and Sine (second 16 bits) from the previous command. 

### The system clock runs internally at 24 MHz generated by the iCE40 `SB_HFOSC` oscillator block (no external clock pin needed).
